# Purchase Intent Service

Сервис оценивает вероятность того, что сессия посетителя интернет-магазина закончится покупкой. 
По поведению на сайте (просмотренные страницы, время на них, показатели Google Analytics, месяц, тип посетителя) модель возвращает вероятность покупки и готовое решение по порогу.


## Возможности

- Сервис поддерживает предсказание для одной сессии и для батча до 1000 сессий, проверки `/health` и `/ready`, автодокументацию.
- Запросы имеют строгую схему: определены границы значений, допустимые категории, запрещены лишние поля.
- Каждый запрос к `/v1/predict` логируется в Postgres, даже отклоненный: в базу данных попадают фичи, предсказание, задержка и код ответа.
- Проект поддерживает запуск в Docker Compose и в Kubernetes.


## Быстрый старт

Для запуска необходимы uv, Docker, kind, kubectl и make.

```
git clone https://github.com/e-plakutina/purchase-intent-service.git
cd purchase-intent-service
```

Проверка проекта целиком - каждая команда завершается сама:

```
make test       # тесты
make compose    # сервис и Postgres в Docker Compose, запрос к модели и строки из таблицы логов
make kind       # деплой в локальный кластер kind и запрос к модели через port-forward
```

Запуск API локально:

```
make install    # зависимости
make serve      # http://localhost:8000/docs
```

На Windows команды `make` выполняются в Git Bash.

## API

После запуска (`make serve` или `make up`) сервис доступен по адресу `http://localhost:8000`.

| метод | эндпоинт | что возвращает |
|---|---|---|
| POST | `/v1/predict` | вероятность покупки для одной сессии и решение "купит / не купит" |
| POST | `/v1/predict/batch` | вероятности и решения для 1-1000 сессий за один вызов модели |
| GET | `/health` | статус "сервис работает" и версию модели |
| GET | `/ready` | статус "модель загружена, сервис готов принимать запросы"; пока модель не загружена - код 503 |

Интерактивная документация открывается в браузере: [http://localhost:8000/docs](http://localhost:8000/docs). Страницу FastAPI строит сам по схемам запроса и ответа: на ней видны все поля с допустимыми значениями, а кнопка "Try it out" отправляет запрос к модели прямо из браузера. Та же документация в формате для чтения - `/redoc`, схема в формате OpenAPI - `/openapi.json`.

Пример запроса - [`examples/request.json`](examples/request.json):

```
curl -X POST http://localhost:8000/v1/predict -H "Content-Type: application/json" -d "@examples/request.json"
```

```json
{
  "score": 0.314156649241437,
  "purchase": true,
  "model_version": "2.0.0",
  "request_id": "340f2120-53d3-4447-936c-a9f1ec9e226b",
  "latency_ms": 90.19
}
```

- `score` - вероятность покупки;
- `purchase` - решение по порогу 0.27, который хранится вместе с моделью;
- `request_id` - идентификатор запроса, по нему запрос находится в таблице логов.

Все 17 полей запроса обязательные: в обучающих данных нет пропусков. Числовые поля проверяются по границам, `Month` и `VisitorType` принимают только значения, которые встречались при обучении (июнь записан как `June`, январь и апрель в данных отсутствуют). 
Некорректное значение, отсутствующее или лишнее поле, тело не в формате JSON дают код 422.

### Батч-предсказания

`POST /v1/predict/batch` принимает `{"rows": [...]}` - от 1 до 1000 сессий в той же схеме, что `/v1/predict`. Из всех строк собирается один DataFrame, и модель вызывается один раз:

```json
{
  "predictions": [
    {"score": 0.314156649241437, "purchase": true},
    {"score": 0.03489807869102427, "purchase": false}
  ],
  "model_version": "2.0.0",
  "latency_ms": 15.06
}
```

Предсказания идут в том же порядке, что строки запроса. Если хотя бы одна строка некорректна, весь запрос отклоняется с кодом 422, а в ответе указан номер строки и поле, например `["body", "rows", 1, "Month"]`. Ограничение в 1000 строк не дает одному запросу надолго занять сервис. `latency_ms` батча - время от сборки DataFrame до предсказаний, без разбора и проверки тела запроса.

## Модель

Данные взяты из открытого датасета [Online Shoppers Purchasing Intention](https://www.kaggle.com/datasets/imakash3011/online-shoppers-purchasing-intention-dataset) (содержит 12 330 сессий за год, покупкой заканчиваются 15.5%).

| метрика (отложенная выборка) | значение |
|---|---|
| PR-AUC | 0.7555 (случайная модель - 0.156) |
| ROC-AUC | 0.935 |
| F1 при пороге 0.27 | 0.678 |
| precision / recall | 0.61 / 0.77 |

PR-AUC на вложенной кросс-валидации = 0.750 +- 0.018: оценка на тесте попадает в разброс по фолдам.

Pipeline сохранен в `artifacts/model.joblib` вместе с паспортом модели: версия, порядок входных полей и порог.

1. `add_features` (`src/purchase_intent/features.py`) - флаги ненулевых значений, среднее время на страницу, приведение типов.
2. `ColumnTransformer` - log1p для счетчиков и длительностей, one-hot для категорий с объединением редких.
3. `HistGradientBoostingClassifier` выбран в качестве модели.

Порог 0.27 подобран по максимуму F1 на out-of-fold предсказаниях обучающей выборки.

- [`notebooks/eda_and_modeling.ipynb`](notebooks/eda_and_modeling.ipynb) - содержит анализ данных, проверка гипотез, сравнение моделей, выбор признаков и порога.
- [`notebooks/model_training.ipynb`](notebooks/model_training.ipynb) - содержит обучение выбранного пайплайна и сохранение бандла.

## Логирование запросов

Каждый запрос к `/v1/predict` записывается в таблицу `predictions`:

| колонка | содержимое |
|---|---|
| `request_id` | идентификатор запроса |
| `ts` | время |
| `model_version` | версия модели |
| `features` | тело запроса (jsonb); тело не в формате JSON сохраняется как `{"raw": ...}` |
| `score` | вероятность покупки; пусто, если предсказания не было |
| `latency_ms` | время обработки |
| `response_code` | код ответа: 200, 422 или 500 |

Батч-запросы в таблицу не записываются: она рассчитана на одно предсказание в строке.

Подключение задается переменной `DATABASE_URL`. Без нее сервис работает, но не логирует.

Команда ниже выводит коды ответа и количество запросов, соответствующее им:

```
docker compose exec db psql -U postgres -d purchase_intent -c "SELECT response_code, count(*) FROM predictions GROUP BY 1"
```

## Развертывание

### Docker Compose

```
make up      # сервис http://localhost:8000/docs и Postgres
make logs    # логи сервиса
make down    # остановить; docker compose down -v удалит в том числе данные базы
```

Сервис стартует после того, как Postgres прошел healthcheck, а `make up` ждет готовности самого сервиса (healthcheck на `/ready`). 
В Dockerfile зависимости ставятся отдельным слоем до копирования кода: после правки кода пересборка не переустанавливает библиотеки.

### Kubernetes

```
make kind-deploy    # собрать образ, загрузить в kind, применить манифесты
make kind-down      # удалить кластер
```

Манифесты лежат в `k8s/`.

**`deployment.yaml`** описывает, как запускать сервис:

- **Две реплики.** Kubernetes держит два одинаковых пода: если один упадет, второй продолжит отвечать, пока первый перезапускается.
- **Три проверки состояния (пробы):**

  | проба | эндпоинт | что делает Kubernetes |
  |---|---|---|
  | startupProbe | `/health` | дает поду до 60 секунд на запуск и загрузку модели; пока проба не пройдена, остальные пробы не выполняются |
  | livenessProbe | `/health` | если сервис перестал отвечать, перезапускает контейнер |
  | readinessProbe | `/ready` | пока модель не загружена, не отправляет на под запросы |

- **Ресурсы на один под:** гарантировано 0.1 ядра CPU и 256 МБ памяти (`requests`), максимум - 1 ядро и 512 МБ (`limits`). При превышении лимита памяти Kubernetes перезапускает контейнер.

**`service.yaml`** дает обоим подам один постоянный адрес внутри кластера: запросы на порт 80 Service распределяет между подами на порт 8000. Тип ClusterIP означает, что адрес доступен только внутри кластера; снаружи к сервису обращаются через `kubectl port-forward` (так делает `make kind`).

## Разработка

`make` без аргументов показывает все команды:

| команда | что делает |
|---|---|
| `make install` | зависимости всех групп и пакет проекта |
| `make data` | скачивает датасет в `data/` |
| `make serve` | API локально с перезагрузкой при изменении кода |
| `make test` | тесты |
| `make lint` / `make format` | проверка и форматирование кода (ruff) |
| `make load` | нагрузочное тестирование (Locust) |
| `make bench` | замер батч-эндпоинта: 1 строка против 500 |

Требуется Python 3.11-3.12, версии библиотек закреплены в `uv.lock`. Зависимости разделены на группы, чтобы Docker-образ не содержал библиотек для исследования:

| группа | что входит | зачем |
|---|---|---|
| основные | fastapi, uvicorn, pydantic, pydantic-settings, psycopg, pandas, numpy, scikit-learn, joblib | сервис и модель |
| data | kagglehub | скачивание датасета |
| notebooks | matplotlib, seaborn, ipykernel | ноутбуки |
| dev | pytest, httpx2, locust, ruff, pre-commit | тесты, нагрузка, линтер |

Настройки сервиса читаются из переменных окружения или файла `.env`, список - в [`.env.example`](.env.example). Ноутбуки запускаются с ядром из `.venv` проекта: они импортируют пакет `purchase_intent`.

Тесты (`tests/`):

- `test_api.py` - контракт: отказ с кодом 422 на некорректные запросы;
- `test_smoke.py` - структура ответа, порог, детерминизм;
- `test_features.py` - преобразование признаков;
- `test_logging.py` - логирование запросов с любым кодом ответа;
- `test_batch.py` - батч-эндпоинт: порядок и совпадение score с `/v1/predict`, границы размера батча.

## Нагрузочное тестирование

Нагрузка подавалась с помощью Locust на сервис в Docker Compose: один процесс uvicorn и Postgres для логов. Виртуальный пользователь отправляет `POST /v1/predict` в 10 раз чаще, чем `GET /health`, и делает паузу 0.5-1.5 секунды между запросами. Каждый прогон длится 60 секунд, результаты - в `loadtest/results/`.

Нагрузочное тестирование выполняется командой `make load`.

| пользователи | RPS | median, мс | p95, мс | max, мс | ошибки |
|---|---|---|---|---|---|
| 10 | 9.2 | 53 | 110 | 176 | 0 |
| 50 | 29.2 | 730 | 1200 | 1641 | 0 |
| 100 | 29.6 | 2400 | 2900 | 3617 | 0 |

При 10 пользователях сервис не нагружен: RPS 9.2 почти совпадает с тем, что пользователи могут отправить при паузе около секунды, медиана - 53 мс, p95 - 110 мс.
Уже при 50 пользователях сервис достигает предела около 29-30 запросов в секунду: при переходе к 100 пользователям RPS не растет (29.2 и 29.6), а лишние запросы ждут в очереди, поэтому медиана растет с 730 до 2400 мс.

При 10 пользователях p95 больше медианы на 57 мс - это обычный разброс времени ответа, при 50 пользователях разрыв резко вырастает до 470 мс, а при 100 почти не меняется (500 мс), потому что очередь сдвигает вверх все время ответа целиком.
Даже у `/health` медиана времени ответа выросла с 4 мс без нагрузки до 500 мс при 100 пользователях: сервис запущен одним процессом и обрабатывает запросы по одному, поэтому быстрые запросы ждут своей очереди вместе с предсказаниями.

Ошибок не было ни в одном прогоне, и все запросы записаны в Postgres, то есть перегрузка проявляется как замедление, а не как отказы; поднять предел можно несколькими процессами uvicorn (`--workers`) или несколькими репликами.

## Замер батч-эндпоинта

Замер выполняется командой `make bench`: медиана `latency_ms` из 10 повторов для батча из одной строки и из 500 строк в одном запросе.

| строк в запросе | latency_ms |
|---|---|
| 1 | 15.06 |
| 500 | 19.39 |

500 строк обрабатываются всего в 1.3 раза дольше одной: каждая дополнительная строка добавляет около 0.009 мс, а около 15 мс - постоянная цена одного вызова pipeline, поэтому в пересчете на строку батч почти в 400 раз дешевле.
